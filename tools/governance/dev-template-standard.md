# PA 개발 템플릿 표준 v2.0 (안)

> 기존 RPA 방법론(2019~) 템플릿을 기반으로, 2026-05 방법론 공유 회의 내용과 Gap 분석을 반영한 개선안.
> 대상: Power Automate Desktop(데스크톱 흐름) 중심 + 클라우드 흐름 적용 지침 포함.

---

## 1. 기존 템플릿 구조 (유지)

기존 구조는 검증된 뼈대이므로 그대로 유지한다.

```
Main
 ├─ StopFunc      : 시작 전 실행 중 프로그램 종료 (리소스 정리)
 ├─ InitFunc      : 전역변수 선언, 로그 경로/파일명 설정, 폴더 생성
 ├─ GetConfig     : 기준정보 로드 (SharePoint/로컬 엑셀)
 ├─ 본 프로세스    : 업무 로직
 │    ├─ 정상 완료 → MailFunc(완료)
 │    └─ 오류 발생 → ErrorFunc → (에러카운터 MAX) → MailFunc(오류)
 ├─ ErrorFunc     : 오류 자동 호출, 화면 캡처, 에러카운터 관리
 ├─ MailFunc      : 완료/오류 메일 (결과 파일, 로그, 캡처 첨부)
 └─ LogFunc ★필수 : 모든 흐름 시작·종료 로그, 세부 단계 로그, 오류 즉시 로그, 에러카운터 증감 로그
```

## 3. 명명 규칙 표준 (G1)

### 3.1 솔루션

```
{조직코드}_{업무영역}_{과제명}
예: DKS_HR_입사자온보딩
```

- 솔루션 버전: `주.부.빌드.0` — 운영 배포 시 주/부 증가, 개발 반복은 빌드 증가
- 게시자(Publisher): 조직 공용 게시자 1개 통일 (`{조직코드} RPA`, 접두사 `{소문자조직코드}`)

### 3.2 흐름 (데스크톱/클라우드)

```
[{조직코드}-{업무영역}-{순번}] {과제명}_{역할}
예: [DKS-HR-001] 입사자온보딩_Main
    [DKS-HR-001] 입사자온보딩_GetConfig
    [DKS-HR-001] 입사자온보딩_본프로세스
```

- 역할 접미사는 템플릿 함수명 그대로: `_Main`, `_StopFunc`, `_InitFunc`, `_GetConfig`, `_ErrorFunc`, `_MailFunc`, `_LogFunc`, `_본프로세스`(또는 `_Biz{순번}`)
- 순번은 과제 단위 3자리. 과제 목록은 거버넌스 시스템의 과제 대장(Dataverse)에서 채번

### 3.3 변수

| 종류 | 규칙 | 예 |
|---|---|---|
| 전역(입출력) | PascalCase + 접두사 | `In_ConfigPath`, `Out_ResultCount` |
| 지역 | camelCase | `rowIndex`, `targetFile` |
| 상수(Config 유래) | UPPER_SNAKE | `MAX_RETRY`, `MAIL_TO` |
| 자격증명 참조 | `Cred_` 접두사 | `Cred_SAP`, `Cred_Portal` |

### 3.4 로그/산출물 폴더

```
C:\RPA\{과제코드}\
 ├─ Logs\{yyyyMMdd}\
 ├─ Capture\{yyyyMMdd}\
 ├─ Input\
 ├─ Output\
 └─ Temp\        ← 실행 종료 시 InitFunc 다음 실행에서 정리
```

## 4. 오류 분류 체계 + 재시도 정책 (G2)

### 4.1 오류 3분류

| 분류 | 정의 | 예 | 기본 처리 |
|---|---|---|---|
| **S (System)** | 일시적 시스템 오류 — 재시도로 해결 가능 | 네트워크 타임아웃, 화면 로딩 지연, 파일 잠금 | **자동 재시도** (백오프) |
| **B (Business)** | 업무 규칙 위반 — 재시도 무의미 | 승인 권한 없음, 기준정보 불일치 | 해당 건 skip + 오류 대장 기록, 계속 진행 |
| **D (Data)** | 입력 데이터 문제 | 필수값 누락, 형식 오류 | 해당 건 skip + 오류 대장 기록, 계속 진행 |

### 4.2 ErrorFunc v2 동작

```
오류 발생
 ├─ LogFunc(오류 즉시 기록 + 분류코드)
 ├─ 화면 캡처 (§6.4 마스킹 적용)
 ├─ 분류 판정 (S/B/D)
 │   ├─ S → RetryFunc: 대기(10초→30초→60초 백오프) 후 재시도, MAX_RETRY(기본 3) 초과 시 중단
 │   ├─ B/D → 오류 대장에 건 단위 기록 → 다음 건 진행 (배치 계속)
 └─ 치명 오류(MAX 초과/예상 외) → MailFunc(오류) + 중앙 로그 상태 'Failed'
```

- **에러카운터는 유지하되 "건 단위 skip 카운터"와 "치명 오류 카운터"를 분리**
- 완료 메일에 skip 건수 + 오류 대장 요약 포함 → "성공이지만 3건 수동 처리 필요" 같은 상태 표현 가능

## 5. CheckpointFunc — 체크포인트/재개 (G3)

장시간 배치(수백 건 처리)용. 짧은 과제(<10분)는 생략 가능.

- 처리 단위(예: 행)마다 진행 위치를 체크포인트 파일(`Temp\checkpoint.json`) 또는 중앙 실행 이력에 기록
- InitFunc에서 체크포인트 존재 확인 → 있으면 "이어서 실행" 여부를 Config로 결정
- 정상 완료 시 체크포인트 삭제

```
checkpoint.json 예:
{ "runId": "...", "lastCompletedKey": "사번2024-1037", "processedCount": 412, "updatedAt": "..." }
```

## 6. LogFunc v2 — 로컬 + 중앙 이중 기록 (G4, G9, G10)

### 6.1 이중 기록

- **로컬**: 기존 그대로 (파일 로그 — 네트워크 단절 시에도 기록 보장)
- **중앙**: Dataverse `실행 이력` 테이블에 흐름 시작/종료/오류를 기록 (오케스트레이터 프레임워크의 데이터 원천)

| 중앙 기록 시점 | 기록 내용 |
|---|---|
| Main 시작 | runId 생성, 과제코드, 머신명, 계정, 시작시각, 상태=Running |
| 본 프로세스 진행 | processedCount 주기 갱신 (N건마다 1회 — API 한도 고려) |
| 오류 발생 | 오류 분류코드, 메시지, 캡처 파일 경로 |
| Main 종료 | 상태=Succeeded/Failed/PartialSuccess, 종료시각, 처리/skip 건수 |

- 중앙 기록 실패 시: 로컬 로그에 남기고 **과제는 계속 진행** (중앙 로깅이 업무를 막으면 안 됨)

### 6.2 중앙 테이블 설계 (Dataverse — 거버넌스 시스템 공용)

```
rpa_실행이력 (rpa_runhistory)
 runId | 과제코드 | 흐름명 | 머신 | 계정 | 시작/종료시각 | 상태 | 처리건수 | skip건수 | 오류코드 | 로그경로

rpa_오류대장 (rpa_errorledger)
 runId | 건 식별자 | 오류분류(S/B/D) | 메시지 | 캡처경로 | 처리상태(미처리/수동완료)

rpa_과제대장 (rpa_taskmaster)
 과제코드 | 과제명 | 담당자 | 스케줄 | SLA | 템플릿버전 | 상태(개발/운영/중지)
```

### 6.3 Heartbeat — 미실행 감지 (G9)

- 과제 대장에 스케줄(예: 평일 09:00) + 허용 지연(예: 30분) 등록
- 거버넌스 시스템의 감시 흐름이 주기 실행: "예정 시각+허용 지연까지 실행 이력이 없으면" 담당자 Teams/메일 알림
- **과제가 죽어도 알림이 오는 유일한 방법** — 과제 스스로 보내는 메일에 의존하지 않음

### 6.4 개인정보 마스킹 (G10)

- 로그 기록 전 마스킹 함수 통과 필수: 주민번호/카드번호/계좌번호/전화번호 패턴 자동 마스킹
- 화면 캡처: 개인정보 화면이 뜨는 단계에서는 캡처 생략 플래그 사용 (`SKIP_CAPTURE` 구간 지정)
- 메일 첨부 전 첨부물 마스킹 확인 체크리스트 (§11)

## 7. GetConfig v2 — 환경 분리 (G5)

우선순위 계층으로 조회 (위가 우선):

```
1. 솔루션 환경변수 (Environment Variables)   ← dev/prod 자동 전환, 배포 시 값만 교체
2. Dataverse 설정 테이블 (rpa_config)        ← 운영 중 변경 가능한 값
3. SharePoint/로컬 엑셀                       ← 기준정보 대량 데이터 (기존 방식 유지)
```

- **환경 의존 값(URL, 경로, 메일 수신자, 환경 ID)은 반드시 1번 환경변수로** — 엑셀에 하드코딩 금지
- 데스크톱 흐름에서 환경변수 직접 접근이 제한되는 경우: 클라우드 흐름(트리거 측)이 환경변수를 읽어 데스크톱 흐름 입력 변수로 전달하는 패턴 표준화
- 기준정보 엑셀은 유지하되 위치 자체는 환경변수로

## 8. CredFunc — 자격증명 표준 (G6)

| 저장소 | 용도 | 우선순위 |
|---|---|---|
| **PAD Credential(CyberArk/Azure Key Vault 연동)** | 대상 시스템 로그인 | 1순위 (Managed Env 필요 시) |
| **Windows Credential Manager** | 로컬 머신 종속 자격증명 | 2순위 |
| 흐름 입력 변수(암호화) | 클라우드→데스크톱 전달 | 제한적 |

**금지 사항 (준수 검사 대상):**
- 흐름 내 하드코딩 비밀번호 ❌
- 엑셀/텍스트 파일에 평문 비밀번호 ❌
- 로그에 비밀번호 출력 ❌ (LogFunc 마스킹이 2차 방어)

## 9. ALM 배포 표준 (G7)

기존: 수동 zip 내보내기 → 가져오기. **v2: Power Platform Pipelines 기반.**

### 9.1 환경 구성 (초안 — 환경 전략 상담과 연동)

```
개인 개발(Developer) → 통합 DEV → TEST(UAT) → PROD
```

### 9.2 배포 규칙

| 항목 | 규칙 |
|---|---|
| 솔루션 형식 | DEV까지 Unmanaged, TEST/PROD는 Managed |
| 연결 참조 | 반드시 솔루션에 포함, 배포 시 Pipelines가 매핑 |
| 환경변수 | 값은 배포 대상 환경에서 입력 (기본값에 dev 값 넣지 않기) |
| 배포 승인 | TEST→PROD는 Pipelines 확장(`OnApprovalStarted`)으로 승인 게이트 — 담당 팀장 Teams 승인 |
| 배포 이력 | Pipelines 자체 이력 + 거버넌스 대시보드 연동 |
| 수동 zip 배포 | **금지** (긴급 시 예외 절차 + 사후 등록) |

### 9.3 솔루션 구성 표준

```
{조직코드}_{업무영역}_{과제명}     ← 과제 솔루션 (흐름 + 연결참조 + 환경변수)
{조직코드}_Common_Library         ← 공통 라이브러리 (별도 솔루션, 별도 배포 주기)
{조직코드}_{고객사}_Library       ← 전용 라이브러리
```

- 공통 라이브러리는 하위 호환 유지 원칙 (기존 입출력 변수 시그니처 변경 금지, 변경 시 새 버전 함수 추가)

## 10. 템플릿 준수 자동 검사 (G8) — 거버넌스 시스템 연계

"적용 방식의 개인차" 문제는 문서만으로 해결 불가. **자동 검사**로 강제한다.

거버넌스 시스템(별도 구축 중)의 검사 흐름이 주기적으로:

| 검사 항목 | 방법 |
|---|---|
| 명명 규칙 준수 | Inventory API로 전체 흐름명 조회 → 정규식 검사 |
| LogFunc 포함 여부 | Dataverse `workflow.clientdata`(클라우드 흐름 정의)에서 LogFunc 호출 존재 확인 |
| 템플릿 함수 세트 존재 | 과제 솔루션 안에 `_Main`/`_InitFunc`/`_ErrorFunc`/`_MailFunc` 흐름 존재 확인 |
| 하드코딩 URL/비밀번호 의심 | 흐름 정의 텍스트 패턴 검사 (http://, password= 등) |
| 연결참조/환경변수 사용 | 솔루션 컴포넌트 검사 |
| 결과 | 위반 시 담당자에게 Teams 알림 + 거버넌스 대시보드에 준수율 표시 |
